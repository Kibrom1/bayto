# Bayto work plan

2026-09-28 · Owner: Kibrom · Status: ready to start

This plan turns the roadmap (M0–M6 in [product-design.md](product-design.md)) into concrete tasks. M0–M3 are broken down to the task level; M4–M6 stay at deliverable level and get detailed when M3 lands. Estimates assume one developer working part-time (about 15–20 hours a week) and are rough.

**Status (2026-10-04):** M2–M6 are built and merged on `main` (M3.12 cost meter included). Floor-policy and acp/1 protocol direction confirmed 2026-10-04 (see Decisions section); only the pricing/billing decision remains open there. Open: M0.5/M0.6 and M1.10–M1.16, which need the host's `sbx` CLI. **Next up:** run M0.5 and the M1.11–M1.14 measurements on the Mac, then the live checks for M1.15 (see its note below), then the MVP exit test.

A session whose sandbox is gone or was never created gets a new distinct `orphaned` status (product-owner-confirmed: not `active`, not the generic failure status, so a future recovery flow can specifically target it) instead of being relaunched. Two real correctness gaps found and fixed in already-merged code: `ModeratorRunner.run_once()` (M2.7) now unconditionally checks for an outstanding, unanswered assignment before computing a fresh floor decision (covers both a real restart and an ordinary transient hiccup mid-loop; the runner never needs to know which case it's in). `POST /sessions/{id}/stop` (M2.8) now also records its `reason` as a durable message (`synthesize` turned out to already be durable via the `stopping`/`cancelling` status split itself, a correction to the architect's assumption -- see docs/decisions.md). `reconcile_on_startup` and the app's `lifespan` both tolerate `SandboxProvider.reconcile()` or the whole reconciliation step failing (no `sbx` CLI, an unreachable Postgres at boot) without ever failing app startup. ## M3 — Bayto room UI

Breakdown drafted by product-owner, reconciled with architect's feasibility/sequencing pass (see docs/decisions.md, 2026-09-30) -- not a human decision. M3.1–M3.5 are backend-only with no frontend dependency and can start immediately regardless of the still-open frontend-engineer staffing question (pending human decision); M3.6–M3.12 are blocked on that staffing decision.

- [x] **M3.1** Backend: query endpoints -- `GET /sessions/{id}` returns status, round count, running token/cost usage vs. budget, AND per-`SessionAgent` turn counts (for M3.9's speaking-time meter); `GET /tasks` (list) for the task board, including a task→session→artifact join for "output artifact link if any"; `GET /modes` returns available modes with tunable-parameter defaults; `GET /agents/templates` returns the M2.11 seeded templates (id, name, system_prompt, stance, model tier). All read-only, tested, documented alongside the M2.8 REST surface. No frontend dependency -- backend-only, can start immediately. `orchestrator/src/orchestrator/moderator/budget.py` (new) extracts `session_usage(sessionmaker, session_id)` from `ModeratorRunner._budget_exceeded`'s aggregate query (M2.7), shared by both rather than a second copy that could drift. `GET /sessions/{id}` computes `round` by reading back `max(Turn.round)` (no new round concept -- both floor policies already assign it at write time). `GET /tasks`'s `status`/`last_session_id` are derived from the task's most-recently-*started* session (`ORDER BY started_at DESC NULLS LAST`, so an unstarted session never outranks a real one unless it's the task's only session); `output_artifact_id` joins to that session's `type="synthesis"` `Artifact` specifically, never `minority_report`; no pagination (flat list, current task volume is dozens not thousands). `GET /modes` reads `modes/<name>.yaml` live via `resolve_mode()` (source of truth everywhere else in this system), not `Mode.stop_rules_json` (M2.11 disclosed these aren't kept in sync); a broken/missing mode file is skipped, not a 500 for the whole list (same failure-isolation principle as M2.9's reconcile routine). `GET /agents/templates` filters to `kind="native"`, exposing `Agent.model` as-is (no tier-computation logic exists). New `api/modes.py`/`api/agents.py`; `GET /tasks`/`GET /sessions/{id}` land in the existing `api/tasks.py`/`api/sessions.py`.
- [x] **M3.2** Backend: participant lifecycle -- add/mute/remove a participant mid-session (orchestrator support; none of these three operations exist anywhere in M2's REST or `Conversation` surface today). Prerequisite for M3.9's roster-panel controls. No frontend dependency -- backend-only, can start immediately. `POST /sessions/{id}/participants/{agent_id}/{mute,unmute,remove}` and `POST /sessions/{id}/participants` (add), all gated on the session being in a live status (`active`/`needs_human`), all in `api/sessions.py`. Remove is a new nullable `SessionAgent.removed_at` column (migration) rather than a hard delete -- replay-safe, keeps the participation record, and a prior Turn row stays fully visible (Turn rows are immutable throughout this system). For floor-control purposes a removed participant folds into the exact same `ConversationView.muted` set a muted one does -- no new FloorPolicy-layer concept needed. Two real pre-existing gaps found and fixed while verifying the architect's "should already work" claims, as instructed: `RaiseHandFloorPolicy.next()` never filtered `raised` by `view.muted` anywhere (round-robin's `next_seat()` already did) -- a muted participant, including one explicitly ADDRESSED, could still win the floor; and `ModeratorRunner`'s hand-raise-scorer personas list was a constructor-time-frozen snapshot, never updated for a mid-session mute or add -- replaced with a fresh per-call DB query (`_current_personas`), which also incidentally made the mid-session "add" case work for raise-hand mode at all (a late joiner wasn't in the frozen list, so the scorer could never have surfaced them).
