# Bayto project analysis: 2026-10-18

Where the project stands, what could go wrong, and what to do first. Facts below come from the code and from commands run on 2026-10-18 on commit `6011c53` (plus `a047dc6` and `d17ff84`, which are committed but not yet merged). Where something is an inference, it says so.

## Summary

Bayto is functionally complete for its MVP: task board, session setup, the room, four modes (including Build), human seat, memory, usage metering. A real Build session has already made a commit on its branch. What is missing is proof at scale (the MVP exit test has not run, and Build has no scripted live run) and two safety gaps that matter before anyone points Build at a repository they care about.

## Findings, most serious first

### 1. Build agents can write into the repository's `.git` (High, from code)

The sandbox mounts the user's repository read-write, including `.git`. The developer role has `Write` and `Edit`. `BUILD_DENY` blocks `git config`, `git push` and the network, but not writing to `.git/hooks/*` or `.git/config` with the file tools. Git runs hooks, `core.fsmonitor` and aliases from those files **on the host**, at the user's next `git commit` or `git status`. This would turn "the model wrote a file" into "code ran on the developer's machine".

Not demonstrated by running a session; the mechanism is standard git behaviour. `build_policy.py` already notes that path-scoped rules such as `Write(tests/**)` are unverified under `claude -p`, so a path deny alone is not enough.

Fix: snapshot `.git/config` and `.git/hooks` before the session, compare after, and mark the change set `blocked` with the reason if they differ. Add `Write(.git/**)` and `Edit(.git/**)` to the denylist as well once B9 shows whether path rules work.

### 2. A second session on the same task switches the repo under the first (High, demonstrated)

`POST /sessions/{id}/start` only checks that session's own status. Nothing stops two sessions starting on one task, and both use the sandbox `sbx-<task_id>` and the same host repository. I reproduced it on a throwaway repo: `prepare_branch` for session A leaves the repo on `bayto/build-aaaaaaaa`; starting session B moves it to `bayto/build-bbbbbbbb` while A's agents are still working in that folder. A's later commits would land on B's branch. The dirty-tree check does not catch this when A has committed everything.

Fix: refuse to start a session while another session of the same task is `starting`, `active`, `stopping` or `needs_human`, with a clear message.

### 3. The Ollama fallback is unproven and partly wrong (Medium, from code)

- **False trigger.** The reactive fallback fires when an agent's reply contains "weekly limit", "usage limit" or "rate limit". A discussion about API rate limiting can switch the session to Ollama permanently (`fallback_active` is saved on the session).
- **Streamed turns ignore it.** When the provider streams (the default), `_stream_turn` runs first and never looks at `fallback_active`; the fallback only applies on the older inbox path. After a real limit hit, every turn first tries Claude again.
- **Text-only.** `crew_notify_fallback.py` sends the last assignment as a bare prompt to Ollama's `/api/generate`. A fallback seat has no tools and no history, so Build cannot use it.
- **Network (unverified).** The team allowlist is `api.anthropic.com`; whether a seat can reach `host.docker.internal:11434` was never checked.

So: if the Claude subscription runs out mid-session, a discussion may continue on a local model with weaker answers; a Build session will stall. M2.15 is unticked in the work plan for this reason.

### 4. No CI, and database tests can skip silently (Medium)

There is no `.github/workflows`. Both test suites run only when someone runs them. The orchestrator tests that need Postgres skip when it is unreachable ("6 database tests were SKIPPED" appeared today before I started the database); `BAYTO_REQUIRE_DB=1` makes them fail instead, but nothing sets it. Python versions are loose: `orchestrator` needs >=3.12, `agent-comms` >=3.10, and cached bytecode shows runs under 3.10, 3.13 and 3.14. Tests were run on 3.13 today.

Fix: one workflow with a Postgres service, `BAYTO_REQUIRE_DB=1`, `pytest`, `npm test`, `tsc -b`.

### 5. Build mode is unproven live (Medium)

B9 is not done. Unverified: that `claude -p` honours the Bash prefix rules and the denylist; how reliably real models end with `VERDICT:`; whether tests that install packages work behind the sandbox allowlist; and whether the `bayto-team` kit finds `agent-comms` and `bayto-mcp` when a repository other than Bayto's own is mounted. Budget is checked between turns only, so one long developer turn can overshoot the default $15 / 600,000 tokens.

### 6. Smaller items

- **UNVERIFIED markers:** 45 occurrences, mostly in `docs/decisions.md` (9), `orchestrator/README.md` (8) and `sandbox/local.py` (6), about the `sbx` CLI's output shapes. Real runs have happened since, so many can now be settled or removed.
- **Human-message race:** a note sent in the instant before a turn starts can be missed if the mirror has not recorded it; the next turn does not recover it.
- **Repo left on the build branch:** after a Build session the user's folder stays checked out on `bayto/build-<id8>`; the UI should say so and offer the switch-back command.
- **No authentication:** documented and deferred to M5; do not expose the port beyond the local machine.

## What is working well

- Pipeline safety valves: an unrouted verdict, exhausted fix cycles, a missing seat or a repeated missing verdict all pause the session with the work kept, rather than looping.
- Decisions are logged (`decisions.md`), design docs exist for the larger features, and the work plan is kept in step with the code.
- Every Build rule that could be unit-tested is: test command validation, evidence check, change set from a real temporary repo, branch preparation.

## Recommended order

1. Findings 1 and 2: both are small and block pointing Build at a real repository.
2. Push and merge the three committed branches (`feat/build-mode`, `fix/interject-ended-session`, `fix/usage-report-404`).
3. B9: the scripted live Build run, with a deliberate check that tries to write into `.git`.
4. CI (finding 4).
5. Ollama: narrow the trigger and apply it to streamed turns, or drop the feature from the docs until it works.
6. Run the MVP exit test (`docs/mvp-exit-test.md`), then clear the UNVERIFIED markers that real runs settled.
