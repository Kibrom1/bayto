# orchestrator

Python (FastAPI) service for M2: sessions, the acp message mirror into Postgres, and SSE streaming.
M2.1 scaffolded the project, M2.2 added the schema, M2.3 adds the mirror watcher. See `docs/work-plan.md`
for M2.4+ (SandboxProvider, conversation core, floor policies, moderator, REST/SSE API).

## Layout

- `pyproject.toml` — uv-managed project (`bayto-orchestrator`); depends on `acp` from `../agent-comms` as an
  editable path dependency (`[tool.uv.sources]`), so it's a real installed package, not copy-pasted code.
- `src/orchestrator/app.py` — FastAPI app with a `/healthz` endpoint.
- `src/orchestrator/db.py` — async SQLAlchemy engine (`postgresql+psycopg`), reads `DATABASE_URL` (defaults to
  `postgresql+psycopg://bayto:bayto@localhost:5432/bayto`).
- `src/orchestrator/models.py` — the M2.2 schema (SQLAlchemy 2 async ORM models): product tables `task`, `agent`,
  `mode`, `session`, `session_agent`, `sandbox`, `turn`, `artifact` (field lists from
  `docs/product-design.md`'s "Data model (core tables)"), plus `message`/`report` acp-mirror tables that mirror
  `agent-comms/src/acp/models.py`'s `Envelope` and `FileTransport.report()`'s dict field for field (see
  `agent-comms/schema/message.v1.json` / `report.v1.json`) — the only addition on each is a `session_id` FK,
  not a wire field, so a mirrored row can be related to the session it came from.
- `alembic.ini` / `alembic/env.py` — async Alembic setup wired to `orchestrator.db.database_url()` and
  `orchestrator.models.Base.metadata`.
- `alembic/versions/85ca6b7d547a_m2_2_initial_schema.py` — the one M2.2 migration, autogenerated against a real
  Postgres and applied/verified there (see below); creates all ten tables in one revision.
- `src/orchestrator/mirror.py` (M2.3) — `MessageMirror`: mirrors an acp `FileTransport`'s messages/reports into
  Postgres using the M2.2 models, and publishes newly-mirrored rows to a `PubSub`. See its module docstring for
  the resume/idempotency design (resumes from `MAX(seq)` per session; `INSERT ... ON CONFLICT DO NOTHING` keyed
  on the wire format's own natural keys — `message_id` for messages, `(message_id, from)` for reports — with a
  report deferred until its message is actually mirrored, since `report.message_id` is a real FK). Watches by
  polling (`run_forever`); `poll_once` is the tested unit.
- `src/orchestrator/pubsub.py` (M2.3) — a small in-process async pub/sub (`asyncio.Queue` per subscriber). Not
  the SSE HTTP endpoint (that's M2.8); this is what a future SSE handler would subscribe to.
- `tests/` — `test_health.py` (the required passing test, no DB needed), `test_acp_dependency.py`, `test_db.py`,
  `test_models_shape.py` (schema/mirror-shape checks, no DB needed), `test_live_migration.py` / `test_mirror.py`
  (run against a real Postgres via `DATABASE_URL`, using the shared `live_schema`/`live_sessionmaker` fixtures
  in `conftest.py`; skip cleanly if none is reachable). `test_mirror.py::test_pubsub_fanout_in_order` needs no
  DB at all.

## Run tests

    cd orchestrator
    uv venv --python 3.12
    uv sync --extra dev
    .venv/bin/pytest -q

All tests pass with no DATABASE_URL set; `test_live_migration.py`'s one test skips instead of failing when no
Postgres is reachable. Point `DATABASE_URL` at a real Postgres (e.g. a throwaway `docker run postgres:16-alpine`
bound to `127.0.0.1`) to also exercise it.

## Database / Alembic — verified live (M2.2, M2.3)

Verified end to end against a real, throwaway Postgres via the local Docker daemon (`postgres:16-alpine`, port
bound to `127.0.0.1` only, a random dev-only password generated at test time, container removed afterwards):
`alembic revision --autogenerate` produced the migration above with no manual edits needed, `alembic upgrade
head` applied it, `alembic check` reported no drift, a real insert/select round-trip through the ORM models
worked (including the `"from"`/`"to"` reserved-word columns on `message`, which Postgres/SQLAlchemy auto-quote),
and `alembic downgrade base` cleanly dropped every table.

M2.3's mirror tests ran against the same kind of throwaway container and passed: message ordering, idempotency
under re-polling, resume-after-restart (a brand-new `MessageMirror` instance only mirrors what's genuinely new),
and a report correctly deferred until its message is mirrored. See the PR description for the exact commands.
